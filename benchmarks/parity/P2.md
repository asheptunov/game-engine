# Fatal renderer diagnostics (P2)

The standalone sample game now terminates with exit code 1 after an unrecoverable CPU or GPU
renderer failure. It preserves the first cause, writes a diagnostic report, and requests pointer
release and renderer cleanup. It never automatically starts another backend. Invalid settings
edits remain recoverable. Engine consumers receive `RenderFailure` through `RenderSession.failure()`
and `onFailure(...)`; the engine library does not terminate its host process.

## Reports and shutdown

`game.ps1` configures the JVM's native fatal-error log under `out/game/crashes/hs_err_pid%p.log`.
`%p` is replaced by the process ID. Before initializing the renderer, `SampleGameMain` writes a
unique timestamped `*-run.txt` file in that directory. It records the process ID, selected scene
and backend, launch dimensions, OS/JVM, expected JVM log path and build identity. The build identity
contains the base Git revision, build time and a SHA-256 fingerprint of source/shader contents,
so uncommitted source builds can be distinguished. It is embedded by `game-build.ps1`.

On a caught fatal failure, `GameCrashHandler` writes the matching `*-crash.txt` and prints its
absolute path to stderr. The report includes the causal exception chain and native result codes
when supplied by the backend, failure phase, cached device/driver information, initialization
state, last submitted render context and last copied completed frame. Camera, dimensions, seed,
sample counts, transport/display settings, clock and lighting values accompany those records.
The report distinguishes missing first-frame/device information from known values.

The report also contains up to 64 recent control/render events, cached timing/resource information
and JVM heap usage. Capturing this context performs no frame-path file I/O. Reports never query
the GPU. The scene's semantic 32-bit hash is a diagnostic fingerprint with possible collisions;
it is not an asset export. Built-in scenes require the matching build and recorded state to
reproduce. Arbitrary in-memory scenes are not exported, and the report explicitly says it cannot
reproduce their content alone. Unrelated environment variables and credentials are not collected.

Cleanup gets two seconds after report writing. An independent watchdog forces exit five seconds
after the first fatal signal, even if a worker, driver teardown, report write or shutdown hook
does not return. Normal fatal termination also uses `Runtime.halt(1)` after the cleanup wait;
JVM shutdown hooks cannot extend the deadline. This policy belongs only to the standalone game.
Cleanup exceptions are secondary and cannot replace the original cause. `cleanupCompleted`
means the host cleanup actions returned; native resource retirement may still be queued.

If a report path cannot be written, the handler prints that path, the write error and report text
to stderr. Startup records and JVM logs help diagnose native crashes that bypass Java handling;
they cannot guarantee a final report after power loss, hard OS termination or process corruption.
The launcher's `out/game/game-stdout.log` and `game-error.log` retain console output until the next
launch. Unique startup/crash reports remain separate. Direct Java launches without the launcher
must supply `-XX:ErrorFile=...` themselves; an unconfigured JVM log path is identified in the record.

## Automated verification

From the repository root in PowerShell:

```powershell
./parity-check.ps1
```

The combined gate includes `fatal-check.ps1 -Backend cpu` and, when a supported GPU is available,
`fatal-check.ps1 -Backend gpu`. The standalone commands build their prerequisites unless given
`-NoBuild`. GPU dependencies must already be installed using `setup-gpu.ps1`. Missing GPU device
coverage remains an explicit partial verification in the combined gate.

Fault fixtures in `tools/parity/` are compiled separately into `out/fatal-check/classes`; normal
game builds contain no fault-selection command or system property. CPU injection throws on an
actual tracing worker. GPU injection throws during kernel initialization or immediately before
device dispatch; it simulates a native error rather than deliberately crashing the graphics driver.
Child processes use the real game owner, fatal handler and session implementations, with no window
or dialog. A parent kills a child that exceeds 15 seconds including JVM/scene startup; the handler's
two/five-second deadlines begin at the fatal signal, not at process launch.

Cases cover CPU failure before/after a completed frame, GPU initialization/execution failure,
missing native modules, an unwritable report directory, duplicate signals, cleanup exceptions,
stalled cleanup, and a failed coordinator that never returns after notifying the application.
Assertions check exit status, report path/content, causal errors, device information or its absence,
startup records, and exactly one renderer startup. Separate library cases check first-failure
identity, late listener notification and continued host execution. A successful CPU child checks
manual relaunch and rejected-edit atomicity.

Each case retains process output and reports under a unique `out/fatal-check/<case>-<id>/` directory.
The combined summary remains `out/parity/summary.json`. Retained milestone evidence is in
`p2-verification/`; it describes the tested machine and fixtures, not certification of every driver
or every possible operating-system failure. Native pointer release has not been human-accepted.

## Manual pointer-release check

After `./fatal-check.ps1 -Backend gpu` has compiled the test fixtures, run this **manual-only**
preview from the repository root. It opens the real sample-game window and arms a CPU worker
failure after ten seconds. Click to capture the mouse and move before the fault fires.

```powershell
$java = 'C:/Users/andri/.jdks/openjdk-23.0.1/bin/java.exe'
& $java --enable-preview '-XX:ErrorFile=out/game/crashes/hs_err_pid%p.log' '-Dgame.jvmErrorFile=out/game/crashes/hs_err_pid%p.log' -cp 'out/fatal-check/classes;out/game/classes;out/gpu/classes;out/gpu/lib/*' game.FatalPreview cpu
```

Repeat with the final argument `gpu`. Observe pointer release, window exit and nonzero process
status; inspect the printed report path. Then launch `./game.ps1 -Backend cpu` normally and verify
the scene remains usable. These manual previews are intentionally excluded from automated gates.
Record human acceptance in `RendererParityRequirements.md` after performing the checks.
